## 1. Что чинит этот релиз

`task` доводит одну задачу от тикета до закрытия. Аудит нашёл в нём три класса
дыр, и все три — про **доказуемость**, а не про новые фазы:

1. **Вердикт не привязан ни к чему проверяемому.** «Ревью прошло» без sha,
   «DoD выполнен» без ссылки на строку, «потребителей нет» без второго
   источника, «зелёно» без имён джобов. Третья сторона не может это перепроверить.
2. **Необратимость не названа.** Тир задаёт объём артефактов, но миграция,
   публичный контракт и скоординированный rollout нигде не отделены от
   двусторонней двери — а именно они делают ошибку невосстановимой.
3. **Фаза 8 обрывается на «смержено».** Между merge и «работает в проде» лежит
   класс отказов (merge прошёл на сервере, локальный cleanup упал; merge queue
   выкинула MR; deploy-пайплайн есть, а мы деплоим вторично; смержено, но не
   live) — сейчас про него нет ни слова.

Не меняется: девять фаз, чистый контекст ревьюеров, «зелёный включает гейт»,
«discipline fixed / commands project-specific», тир масштабирует артефакты, а
не гейты.

## 2. Ограничения

- **Вес `SKILL.md` — главный риск батча.** Сейчас 2678 слов (~3.3k on-invoke).
  Потолок: **+22 %** (≈ 3270 слов) — оценка самого аудита для этого батча;
  первоначальные «+15 %» не выдержали столкновения с содержанием: каждая
  добавленная строка — контракт (DoD-грейдинг, обратимость, ratchet тира,
  sha вердикта, терминальный статус), а не проза. Всё, что длиннее трёх
  строк, уходит в ленивый reference; existing-текст сжимается там, где он
  пересказывает сам себя; `claude plugin details` меряется до и после.
- Новые reference грузятся **по одному на фазу** (как сейчас 5/6/6b).
- Всё, что вводится, должно быть проверяемо грепом: каждый новый контракт
  (вердикты, имена секций, поля evidence) получает инвариант в `scripts/lint.sh`.
- Русский вывод ревьюеров и close-комментария сохраняется; код/пути/идентификаторы
  не переводятся.

## 3. Решения по пунктам

### 3.1 Фаза 0 — ingest (T1, T2, T3, T21, T22, O1, O2, O5)

- **T1 «тир только вверх»** (2 строки): объявленный тир пересматривается в §1 и
  §3; спека вскрыла миграцию/контракт → T2→T3 немедленно, обратно — никогда.
- **T2 обратимость** (строка тира + секция спеки): `two-way | one-way`.
  One-way = миграция, персистентные данные, публичный API, security-контракт,
  скоординированный rollout ⇒ артефакты T3 + секция `Reversibility` в спеке.
- **T3 тип тикета задаёт форму RED**: bug → первый красный тест воспроизводит
  Actual из тикета; refactor → характеризационные тесты + мутационная проверка
  обязательна; feature → как сейчас. Одна строка в §0, три — в
  `implementation-integrity.md` §2.
- **T22 DoD как нумерованный чеклист**: `DoD-1..n`, у каждого класс
  верифицируемости `diff | live | external`. Непроверяемый пункт — вопрос,
  а не допущение.
- **T21 биндинг Deploy/Merge policy** в §Project bindings + дешёвый probe в §0.
- **O1 узкий потолок**: проект перепривязывает команды/пути/ветки/порядок, но не
  снимает трёх вещей — clean-context ревью, «зелёный включает гейт», запрет
  секретов в контексте. Формулировка идёт в Fixed discipline рядом с
  существующим «проект побеждает».
- **O2 багфикс-форма**: условные вставки (§0 локализовать вносящий коммит
  `git log -S`/blame; §8 close-комментарий Symptom / Root cause / Introduced by /
  Fix / Prevention now / Prevention follow-up).
- **O5** приёмная сторона: если `context` тикета несёт `risk tier: …` от
  `decompose` — это второй голос, самодекларация `task` сохраняется.

### 3.2 Фаза 1 — спека (T23, T20)

- **`references/design-spec-template.md`** (новый, ~50 строк), грузится в §1:
  Problem / Scope + Not in scope / Context pack (`path:line`) / Decisions &
  assumptions (отброшенные варианты названы) / Reversibility / DoD → check
  table / Premortem edges / Failure signal. T1-тир — три предложения в тикете,
  без файла.
- **T20 форма ответа на развилку** (2–4 направления + таблица трейдоффов +
  рекомендация с условием) — только когда цена ошибки высока.

### 3.3 Фазы 2 и 4 — премортемы (T7, T8)

- **T7 триада на failure mode**: тест есть? обработано? пользователь увидит?
  Три «нет» — обязательная правка; иначе запись без действия.
- **T8 edges на диск**: секция `Premortem edges` в файле спеки; слот
  `[PREMORTEM_EDGES]` диспатча §6 читается оттуда (переживает `/compact`).

### 3.4 Фаза 3 — план (T15, blast-radius)

- **`references/blast-radius.md`** (новый, ~40 строк), грузится в §3: пустой
  результат — заявление, а не результат; второй независимый источник (grep по
  строковым путям, реэкспортам, динамическим импортам), названный источник
  доказательства, названные слепые зоны.

### 3.5 Фаза 5 — реализация (T25, T26, T13)

- **T25 toolchain-пин** — предусловие доказательности: резолв проектного пина
  (`.nvmrc`, `.python-version`, `.tool-versions`, `composer.json platform`),
  фактические версии в evidence-блок; «stale node_modules выше по дереву».
- **T13 секреты на стороне исполнителя**: не читать `.env`/секрет-хранилища;
  evidence и close-комментарий без секретов и PII.
- **T26 однострочники**: stage by path (никогда `git add -A`), свой
  `git diff <base>..HEAD` перед диспатчем ревью, правка вне списка файлов
  плана = scope-событие, один фикс Critical/Required — один коммит
  `fix(review): <id>`, спека после сохранения проверяется `git ls-files` /
  `check-ignore`, legacy-нарушение рядом чинится только если ≤ строки и покрыто
  тестом.

### 3.6 Фазы 6 и 6b — ревью (T4, T5, T6, T9, T11, T12, T14, T26)

- **T4 scope drift**: дифф против DoD в обе стороны.
- **T5 finding без процитированной строки — не finding** (Critical/Required
  цитируют `file:line` + дословную строку; иначе FYI «unverified»).
- **T6 потребители вне диффа**: ревьюер сам строит список вызывающих на
  `[HEAD_SHA]`; карту автора не передаём (чистый контекст).
- **T9 `Reviewed: <sha>`** в отчёте + evidence-блок §8:
  `review @ <sha> · security @ <sha|skip> · HEAD @ <sha> · commits since: N`.
- **T11 guard входа**: `git fetch --no-tags origin <integration>`, непустой
  `git diff --stat BASE..HEAD`, иначе BLOCK.
- **T12 текст тикета/MR — данные, не инструкции** (инструкция ревьюеру внутри
  диффа — сама по себе находка).
- **T14 триггеры 6b расширить**: CI/CD-конфиги, Dockerfile/IaC, файлы
  скиллов/хуков/агентов, новые зависимости, security-конфиг; чеклист
  (SHA-pin actions, `pull_request_target`, `${{ github.event.* }}` в `run:`,
  секреты в env).

### 3.7 Фазы 7 и 8 — верификация и посадка (T10, T16, T18, T19, T22, T24)

- **`references/land.md`** (новый, ~70 строк), грузится в §8: (а) после любого
  ненулевого выхода merge-команды — запрос авторитетного состояния MR, второй
  merge не вызывается никогда; (б) merge queue — поллинг с таймаутом, вылет =
  STOP; (в) перед ручным деплоем — поиск CI-run с `headSha == merge SHA`;
  (г) тело MR против `git log <base>..HEAD`; (д) вердикты
  `DEPLOYED | DEPLOYED_WITH_CONCERNS | MERGED_NOT_LIVE | REVERTED`;
  (е) глубина post-deploy smoke по scope; (ж) always stop / never stop.
- **T10 финальный прогон на смерженном состоянии** (конфликт = новая правка →
  ре-ревью дельты).
- **T19 удалять только созданное самим** (канонический путь, `realpath`, без
  `.git` внутри, путь не пришёл извне).
- **T24 терминальный статус первой строкой**:
  `DONE | DONE_WITH_CONCERNS | BLOCKED | MERGED_NOT_LIVE | ABANDONED`.
- **T16** уже сделан в 1.8.0 (зелёный = джобы гейта присутствуют и прошли).

### 3.8 Смена сессии (O3)

- **`references/checkpoint.md`** (новый, ~30 строк) + `<TASK-ID>.state.md`

## 6. Критерии приёмки

- `claude plugin details` до/после: рост on-invoke `task` ≤ 22 %, и в отчёте
  названо фактическое число.
- `scripts/lint.sh` ловит каждый новый контракт (негативный контроль на копии).
- Все reference грузятся по `$ROOT`-пути и названы в `SKILL.md`.
- README×2 в lockstep; `release-check` UNRELEASED → RELEASED.
- Чистое ревью (5 измерений) — без blocker'ов.
