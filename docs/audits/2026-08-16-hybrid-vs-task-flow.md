# Аудит: hybrid-flow против task-flow

**Дата:** 2026-08-16
**Источник:** `hybrid-plan`, `hybrid-plan-s`, `hybrid-plan-l`, `hybrid-review`
(8 файлов, ~300 строк; лежали в `src.v2/`, к проекту не относятся — материал
для сравнения)
**Против:** `task-flow:task`, `task-flow:decompose`, `task-flow:ci-gate` + их
references
**Результат:** плагин 1.4.1 → 1.5.0

---

## 1. Что такое hybrid

Не самостоятельный флоу, а **тонкий адаптерный слой над `superpowers`**.
`hybrid-plan` = `writing-plans` + дельта-рубрика; `hybrid-plan-s`/`-l` =
роутеры по размеру задачи поверх `brainstorming`; `hybrid-review` = диспатч
независимого ревьюера + опциональный security-аудитор, а приём фидбека отдан
`receiving-code-review`.

Ценность лежит **только в дельтах** — там, где рубрика добавляет решение,
которого нет в апстриме. Всё остальное — пересказ `superpowers`.

## 2. Структурная разница

| | hybrid | task-flow |
|---|---|---|
| Что это | план + ревью, поверх superpowers | сквозной пайплайн эпик → тикет → merge |
| Границы | заканчивается на verdict ревью | ingest, tracker, live-verify, close, Spent time |
| Детерминированный слой | нет | `ci-gate` (gitleaks, migration-guard, protected-branch) |
| Премортемы | упоминает как линзу | два обязательных, плюс мост в полноценный скилл |
| Ops-поверхность (гранты, миграции, кеши) | нет | отдельная ось в code-review |
| Пропорциональность | три роутера по размеру | одна фиксированная дисциплина |
| Планирование | risk-map, test seams, E→M→C, checkpoints | dependency-first, SPIDR, waves, DoD с truths |
| Язык | RU-скиллы | EN-скиллы, RU-вывод ревью |

Коротко: **hybrid сильнее на уровне «как решить, что и как проверять»,
task-flow сильнее на уровне «как довести до мержа и не соврать про результат»**.

## 3. Что взято (и куда легло)

| Взято | Куда | Зачем |
|---|---|---|
| **Test seams** — выбор шва до написания тестов, реальная граница вместо глубокого мока | `task` фаза 3 (+ фаза 5) | Апстримный TDD-скилл говорит «no mocks unless unavoidable», но не говорит **на каком уровне** тестировать. Зелёный мок при сломанном реальном пути — типовой провал фазы 7 |
| **Blast radius / risk-first ordering** | `task` фаза 3 | Фаза 3 была «упорядочить шаги»; теперь сначала карта потребителей и самое дорогое неизвестное, и оно проверяется первым |
| **Frontier-выбор вопроса** | `task` фаза 0, `decompose` фаза 0 | Было «спроси, если скоуп раздваивается» — без стратегии. Плюс правило «варианты без разных последствий — не вопрос» ложится на твой стиль «рекомендация, а не меню» |
| **Verification assessment** в ревью | `code-review-prompt.md` | Ревьюер обязан отделить «проверил» от «поверил на слово». Молчание об этом читалось как «всё проверено» |
| **Честность про доказательства** | `code-review-prompt.md` | «Tests pass» в описании — это заявление, а не доказательство |
| **Песочница ревьюера**: без сабагентов, без `.env`/секретов | оба prompt-шаблона | Ревью — одна независимая пара глаз; пересказ сабагента ею не является |
| **`git status --short` в скоупе ревью** | `code-review-prompt.md` | Адаптировано: у hybrid это про незакоммиченный worktree, у нас — детектор забытого `git add` (диф выглядит целым, в MR не хватает файла) |
| **Residual risk / unverified assumptions** | `security-review-prompt.md` | То же для threat-model: что не удалось протрассировать |
| **expand → migrate → contract** | `decompose` фаза 2 + `splitting.md` | SPIDR режет то, что *добавляют*. Для смены контракта, от которого уже зависят потребители, вертикального среза не существует — нужна другая ось |
| **Параллелизм только по frontier DAG без пересечения ресурсов** | `decompose` фаза 4 + QA Check 8 | **Реальный дефект:** волны считались только из `depends_on`. Две задачи первой волны, пишущие один файл, — обещание параллелизма, которое не выполняется |
| **Risks + Open questions в артефакте** | `decompose` фаза 6 + `draft-template.md` | Блокирующий вопрос не должен пережить аппрув: либо решён, либо задачи помечены blocked и не уходят в работу |
| **Severity → action** (Required закрывается либо фиксом, либо явным принятием риска; Optional/Nit не становятся обязательной работой) | `task` фаза 6 | Было только «чинить настоящие, шум отклонять». Не хватало обеих границ: и против тихого даунгрейда, и против разрастания задачи из-за нитов |
| **Мост в `superpowers:receiving-code-review`** | `task` фаза 6 | У нас была своя трёхстрочная версия. Тот же паттерн условного моста, что уже есть для `premortem` (1.4.0) |
| **Приоритет инструкций + запрет молчаливого отклонения** | «Fixed discipline» обоих скиллов | Скилл говорит «дисциплина фиксирована», но проектный `CLAUDE.md` может ей противоречить. Побеждает проект — с обязательным упоминанием, от чего отклонились |

## 4. Что отклонено

- **`plan-ceo-review`, `plan-eng-review`, `plan-design-review`,
  `plan-devex-review`.** Их нет ни в одном установленном плагине и нигде в
  `~/.claude` — проверено. Шаги 3–5 `hybrid-plan-l` ссылаются на
  несуществующие скиллы: флоу молча деградирует, а модель дорисует
  правдоподобную «линзу» из названия. Тот же класс отказа, что H-001 в
  премортеме `decompose`.
- **Три роутер-скилла по размеру задачи.** Дублирующиеся описания
  («half-day-to-one-day» против «multi-day»), классификация размера требуется
  до того, как размер известен, и это чистый вес промпта. У нас разделение по
  типу артефакта (`decompose` для эпика, `task` для тикета) — оно однозначно.
- **Слияние находок ревьюера и аудитора по root cause.** У нас сознательно
  наоборот: независимое совпадение двух линз — сигнал приоритета, а не
  дубликат. Взята только метка «подтверждено обоими» по смыслу.
- **Пять осей ревью hybrid как замена нашим.** Наш шаблон шире: DoD/spec
  compliance, ops-поверхность, структурные средства (не только «в чём
  проблема», но и «каким наименьшим движением убрать»), премортем-краевые.
- **RU-тексты самих скиллов.** Плагин публичный: тела скиллов — EN, русский
  остаётся в формате вывода ревью.

## 5. Оставлено на решение

**Пропорциональность.** Единственная идея hybrid, которую я не стал внедрять
сам: `task` одинаково прогоняет 9 фаз и для миграции платежей, и для правки
одной строки в шаблоне. Аргумент «за» текущего поведения записан прямо в
скилле: «не пропускай премортем, потому что задача выглядит простой — именно
тогда дыры и прячутся». Аргумент «против»: на однострочных тикетах цена
ритуала выше пользы, и это подталкивает вообще не запускать `/task`.

Вариант, если решишь: не роутер-скиллы, а один гейт в фазе 0 — «тривиальное
изменение (одна поверхность, без данных/авторизации/миграций/внешних вызовов)
→ фазы 1–4 схлопываются в дизайн из трёх предложений в чате и один премортем;
6b и 8 не трогаем никогда». Реализуется тремя строками, но меняет обещание
«дисциплина фиксирована» — поэтому твоё решение, не моё.
