# task-flow

[![version](https://img.shields.io/github/v/release/umar-s/task-flow?label=version&color=0b7285)](https://github.com/umar-s/task-flow/releases/latest)
[![changelog](https://img.shields.io/badge/changelog-keep--a--changelog-0b7285)](CHANGELOG.md)
[![license](https://img.shields.io/badge/license-MIT-0b7285)](LICENSE)

Плагин для **Claude Code и Codex CLI**: дисциплинированный **пофазовый flow
ведения задачи** плюс **детерминированный CI-гейт**, на который он опирается, —
и скилл `decompose`, который питает оба. Три скилла, один продукт; когда
установлены оба харнесса, ревью каждого изменения уходит модели, которая его
не писала.

> История релизов — [CHANGELOG.md](CHANGELOG.md).

## Пайплайн

```
decompose → task → ci-gate
```

`decompose` режет эпик/фичу/спеку на задачи; каждая задача проходит flow
`task` от начала до конца; `ci-gate` — детерминированный «пол», через который
проходит каждый merge.

## Скиллы

### `decompose` — эпик/фича/спека → декомпозиция на задачи
Превращает одну крупную единицу работы — вольное текстовое описание фичи,
существующий эпик трекера `<TASK-ID>` или спека/design-документ — в
well-formed, связанные зависимостями задачи с полным контрактом из **6
полей** (`name`, `context`, `requirements`, `dod` с `truths`, `story_points`,
`depends_on`), графом `depends_on` и вычисленными волнами параллелизма:

```
0 ingest → 1 requirements → 2 decompose → 3 enrich → 4 graph/waves
→ 5 QA (субагент в чистом контексте) → 6 MD-драфт → 7 tracker sync*
```

`*` опционально: фаза 7 запускается только после явного одобрения драфта,
всегда сначала dry-run, и корректно останавливается на драфте, если трекер не
настроен, — а когда всё же пишет, **перечитывает каждую затронутую задачу** и
сверяет с тем, что отправляла: `ok` от пишущей стороны — заявление, а не
проверка. QA-проход судит поля по качеству, а не по наличию: глагол-цель без
артефакта, прилагательное без метрики, перечисление с «и т.д.» или путь,
которого нет, — находки, а идентификатор, который никто не подтвердил, пишется
как `<placeholder>`, а не выдумывается. Story Points по Фибоначчи
(`1/2/3/5/8/13`) — **опциональная аннотация, не гейт**: разбиение ведут SPIDR/вертикальные срезы/зависимости.
MD-драфт (`docs/decompose/YYYY-MM-DD-<epic>.md`) — самодостаточный основной
артефакт; пуш в трекер (YouTrack и другие адаптеры) — типовое опциональное
дополнение.

Вызов: `/task-flow:decompose` (в Codex — `$task-flow:decompose`) или «нарежь
на задачи», «декомпозируй эпик/фичу», «разбей проект на задачи». Каждый
полученный `<TASK-ID>` дальше подхватывает `task`.

### `task` — пофазовый quality-flow
Проводит один тикет от разбора до закрытия через фиксированные quality-gates:

```
0 ingest → 1 design-spec → 2 premortem(дизайн) → 3 план → 4 premortem(план)
→ 5 TDD → 6 code-review → 6b security-review* → 7 verify live → 8 close
```

`*` условно: security-проход запускается только если диф трогает auth, ввод,
сеть, секреты, data/PII, миграции или гранты. Это **LLM**-слой — gameable и
коррелирует с исполнителем, — поэтому он не заменяет детерминированный гейт, и
наоборот. Одна задача = одна ветка → один MR/PR, CI зелёный (включая гейт) до
merge.

Каждая задача объявляет **тир · тип · обратимость** (тир двигается только
вверх), каждый пункт DoD получает оценку `PASS | FAIL | PARTIAL` со ссылкой на
`file:line` или команду, а close-комментарий начинается с терминального статуса
— `DONE | DONE_WITH_CONCERNS | BLOCKED | MERGED_NOT_LIVE | ABANDONED`, — чтобы
человек или раннер читали исход, не разбирая прозу.

Вызов: `/task-flow:task DEV-475` (в Codex — `$task-flow:task DEV-475`) или
«прогони через наш flow». Дисциплина фиксирована; конкретные команды
трекера/VCS/сборки берутся из файла инструкций проекта — `AGENTS.md` или
`CLAUDE.md`.

С установленным плагином `prediction-protocol` `task` ставит сессию под гейт
прогнозов в начале фазы 5 (`predict-gate: active`), превращает каждый
state-changing шаг — миграции на dev, merge, deploy, каждый `live`-пункт DoD —
в receipt, который грейдит инструмент, читает `docs/evidence/REFUTED.md` в
фазе 0 и переносит строку `predictions:` в evidence-блок. Без плагина те же
строки печатают `predict-gate: absent`, и флоу идёт как раньше.

**Перекрёстное ревью другой моделью.** Когда установлены оба CLI, фазы 6 и 6b
уходят харнессу, который не писал дифф: `templates/xreview/xreview.sh`
заполняет бриф ревью из файла спеки и git, запускает `codex exec` или
`claude -p` только на чтение и в изоляции от сессии автора — без
пользовательских плагинов, чтобы плагин памяти не пересказал ревьюеру историю
реализации, — читает вердикт и пишет `docs/reviews/<TASK-ID>-<sha>-<model>.md`.
Exit `0` — чисто · `1` — блокирует · `2` — ревью не состоялось, и это никогда
не читается как «чисто». Субагент той же модели остаётся объявленным
запасным вариантом.

### `ci-gate` — раскладка детерминированного гейта
Ставит в любой репозиторий переносимый неподкупный «пол» под категории, которые
не ловят ни тесты, ни LLM-ревью:

- **secret-scan** — gitleaks, в pre-commit, pre-push и CI; pre-push сканирует
  коммиты, которые вот-вот покинут машину, по каждому ref (ловит `--no-verify`,
  amend, историю с другой машины) и блокирует push, если git не может сказать,
  что именно уходит
- **migration-guard** — инструмент-агностичный, по путям: forward-only
  неизменяемость + деструктивный DDL только с маркером
  `-- destructive: approved (<причина>)` — причина обязательна; миграция,
  добавленная симлинком, падает (её blob — путь назначения, а не SQL,
  который выполнится)
- **unicode-guard** — в добавленных строках нет bidi-override, zero-width и
  tag-символов (Trojan Source); обычная не-ASCII проза и emoji его не задевают
- **diff-coverage** — порог покрытия по изменённым строкам, опционально: читает
  отчёт, который уже производит тестовый прогон проекта (lcov / Cobertura /
  Clover), и судит только те строки, которых коснулось изменение
- **protected-branch** — запрет force-push + required status checks +
  обязательное ревью владельца на файлы гейта (`CODEOWNERS`): MR под проверкой
  не может править судью (правило платформы, ставится один раз через
  `glab`/`gh`)

Вызов: `/ci-gate` в репозитории. Копирует `ci/`, конфиги gitleaks и pre-commit,
`CODEOWNERS`, CI-файл под GitLab **или** GitHub, печатает команды
protected-branch. Затем `ci/gate.sh --selftest` доказывает, что гейт умеет
падать — заведомо плохие фикстуры судят скрипты, сканер и allowlist этого же
репозитория — прежде чем кто-то поверит его «зелёному»; `ci/scan-text.sh <file>`
сканирует комментарий или описание MR до публикации. Полезная нагрузка шаблона
— в `templates/ci-gate/`.

Требования к хосту: `bash` 3.2+, `git` **2.31+** (скан без `--diff-merges` не
видит секрет, внесённый в merge-коммите, — слои отказываются работать, а не
сканируют меньше обещанного), любой awk, и `pre-commit` 3.2.0+ для локальных
хуков.

Executor-aware для GitLab: вариант под **docker/k8s** (через `image:`) и вариант
под **shell**, который тянет pinned gitleaks с проверкой sha прямо в джобе — без
docker, без правки раннера, без эскалации через docker-group. Одна версия
сканера во всех путях: digest образа в docker/GitHub-джобах, закоммиченный
SHA256 на shell-раннере (перепроверяется при каждом вызове), `rev` по коммиту в
pre-commit. Секрет-скан
инкрементальный (диапазон MR / только новые коммиты на push / полная история по
расписанию).

**Опциональный второй security-проход (GitLab): Codex Security.** Ещё два
include сканируют дифф MR через CLI Codex Security от OpenAI, сохраняют
SARIF-отчёт и восстанавливают код выхода сканера отдельной гейт-джобой. Это
**LLM-сканер, а не слой гейта** — ещё одна модель после 6b из `task`, никогда
не замена secret-scan, migration-guard и unicode-guard. Запускается только для
MR между защищёнными ветками одного проекта; API-ключ (или ChatGPT-логин
приватного shell-раннера) — решение владельца.

## Установка

```
/plugin marketplace add umar-s/devpowers
/plugin install task-flow@devpowers
```

В Codex CLI:

```
codex plugin marketplace add umar-s/devpowers
codex plugin add task-flow@devpowers
```

Дальше — по пайплайну: `/task-flow:decompose` режет эпик на задачи,
`/task-flow:task DEV-475` проводит каждую через quality-flow,
`/task-flow:ci-gate` один раз на репозиторий раскладывает гейт, через который
они все проходят на merge (в Codex те же имена начинаются с `$`).

## Claude Code и Codex

Флоу в обоих один; харнесс виден вот где:

| | Claude Code | Codex CLI |
|---|---|---|
| Вызов | `/task-flow:task <TASK-ID>` | `$task-flow:task <TASK-ID>` |
| Правила проекта | `CLAUDE.md`, первая строка `@AGENTS.md` | `AGENTS.md` (единственный файл, который он читает) |
| Свежий субагент | Agent tool | порождённый субагент (`.codex/agents/reviewer.toml`) |
| One-way команда без квитанции (prediction-protocol) | спрашивает | deny — открыть квитанцию, повторить |
| Ревьюер фаз 6 / 6b | `xreview.sh --by codex` | `xreview.sh --by claude` |

В `templates/agents/` — скелеты: `AGENTS.md` с bindings task-flow и
`## Code Review Rules`, `CLAUDE.md`, который его импортирует, `.codex/config.toml`
проекта, read-only роль ревьюера и `.codex/rules/git.rules` (commit выходит из
песочницы, push спрашивает человека, force-формы, видимые prefix-правилу,
запрещены).

## Волна задач параллельно

Задачи одной волны `decompose` не пишут одни и те же файлы, поэтому каждой
можно дать свою сессию одновременно. `templates/wave/task-wave.sh` — один раз
скопировать в `scripts/` проекта — их запускает: на каждый готовый issue
(открыт, метка `builder:claude` или `builder:codex`, все блокирующие закрыты) —
git worktree `../<repo>-<N>` на ветке `task-<N>` и окно tmux с тем харнессом,
который называет метка, и уже вызванным `task`:

```bash
bash scripts/task-wave.sh --dry-run   # что будет запущено
bash scripts/task-wave.sh             # запустить; или номера: … 12 14
tmux attach -t wave-<repo>            # Ctrl-b w — список окон
```

Сессии остаются интерактивными — `task` спрашивает на ingest и перед мержем, —
а скрипт ничего не мержит, не пушит и не удаляет из вашего; одновременно
работает один запуск на репозиторий. Существующий worktree
подхватывается; `--base <branch>` — старт от интеграционной ветки, отличной от
ветки по умолчанию. Следующая волна — когда эта смержена. Трекер — GitHub
Issues через `gh`.

## Маршрутизация скиллов (вставить в `AGENTS.md` или `CLAUDE.md` проекта-потребителя)

`description` скиллов конкурирует в сессии с десятками чужих; таблица
маршрутизации в файле инструкций проекта — то, что заставляет модель брать их
самой (в Codex имена пишутся через `$`):

```markdown
## Skill routing
- Тикет / id задачи (`DEV-475`, `#123`, «сделай задачу …») → `/task-flow:task`
- Эпик, описание фичи или спека, которую надо нарезать на задачи → `/task-flow:decompose`
- «добавь CI-гейт», «secret scan», «migration guard», новый репозиторий → `/task-flow:ci-gate`
- Не уверен, подходит ли скилл → вызови его; отказ внутри скилла дешевле,
  чем прогон флоу без него.
```

## Заметки по дизайну
- Гейт детерминирован намеренно: LLM-ревьюер оптимизирует под «зелёно», а не под
  «верно», и делит слепые зоны с исполнителем. Секреты и деструктив — неподкупная
  проверка; логика — LLM-проход.
- Масштабируется церемония, а не гейты: фаза 0 в `task` объявляет тир
  (тривиальная / обычная / высокая ставка), и он задаёт размер **артефактов**, а
  не набор фаз. Фаза, которая ничего не нашла, так и пишет — придуманный риск
  превращается в придуманное требование, и на мелком тикете это самый вероятный
  способ тяжёлым флоу испортить изменение вместо того, чтобы его защитить.
- `dep/SCA` идёт закомментированным стабом — языко-зависимый, вписывается под репо.
- migration-guard падает **closed** (exit 2), если в CI не может вычислить base
  ref или прочитать миграцию, которую обязан проверить, — гейт, который тихо
  пропускает, хуже отсутствующего. Убедись, что он умеет падать, до того как
  поверишь его «зелёному».
